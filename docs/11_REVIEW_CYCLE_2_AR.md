# مراجعة الدورة الثانية وتسليم النسخ — Octopus S1

**التاريخ:** 27 أكتوبر 2026، UTC.  
**التقرير المراجع:** OS1-LOCAL-002 / Revision 1 عند `ae9b31b`.  
**مصدر APK Dev 0.1.1:** `9d4a1ce065834cfc73dfa153b60d007249838dda`.

## نتيجة المراجعة
قراءة التغييرات تدعم معالجة R1–R4: بوابة المصدر وXML وإصدار Unity،
توقف إطار Pause قبل محاكاة اللعب، snapshot/restore بدل git restore،
وحزمة الاختبارات والسجل المشترك لرقم الإصدار. أضيف اختبار للسقوط بعد إعادة
المشهد مع مزامنة transforms الفيزيائية.

نجح هنا تشغيل **12/12** من tests/release-gates.Tests.ps1 باستخدام
PowerShell 7.4.6 على Linux، و**2/2** من اختبارات إعداد Python.
هذه إعادة تحقق مستقلة لبوابات السكربت، وليست إعادة تشغيل Unity.
أما **EditMode 5/5 وPlayMode 11/11** ونتيجة بناء Android فهي نتائج الوكيل
المحلي؛ لم يُنزّل APK أو XML المحليان لهذه المراجعة ولم يُختبر هاتف هنا.

المراجعة تسمح بالانتقال إلى التسليم وتجربة الجهاز. لا تطلب إعادة تنفيذ
R1–R4 من الصفر أو إعادة بناء Dev 0.1.1 لمجرد تحديث الوثائق أو تثبيت gh.
عند اكتشاف عيب فعلي جديد، أصلحه باختبار مناسب ونسخة برقم جديد.

## أداة gh المحمولة ضمن النطاق المصرح
سبق أن أجاز أمر 002 استعمال CLI المحمول الرسمي لتسليم مسودة للمالك.
تنزيله وفكه خارج المستودع خطوة قابلة للعكس لازمة لذلك التسليم، فلا يحتاج
موافقة تنزيل متكررة أو تثبيت MSI/UAC أو تغيير PATH العام.
هذه ليست موافقة على نشر عام أو اشتراك أو مشاركة بيانات اعتماد.

تحققت المراجعة من [إصدار GitHub CLI الرسمي v2.103.3](https://github.com/cli/cli/releases/tag/v2.103.3)
و[بياناته الرسمية](https://api.github.com/repos/cli/cli/releases/latest) في وقتها:

| المعمارية | أرشيف ZIP | الحجم بالبايت | SHA-256 |
|---|---|---|---|
| Windows x64 | gh_2.103.3_windows_amd64.zip | 15197187 | `98d0cfa794721665d7973dd728c78aff7bd836d58f10f6d7a03568eccb0a22e0` |
| Windows ARM64 | gh_2.103.3_windows_arm64.zip | 13637549 | `197211c98687d7770ac331fe8a3b6c198c389108c1536cdbedf659fe4703e484` |

رابط الأرشيف تحت:
https://github.com/cli/cli/releases/download/v2.103.3/
ويلي ذلك اسم ZIP المناسب أعلاه. لا تستعمل MSI بدل ZIP لهذه الخطوة.
يتحقق الوكيل من معمارية الجهاز، وينزل الملف ويفحص SHA-256 قبل تشغيله،
ويفكه مثلًا في مجلد إصدار مخصص داخل %LOCALAPPDATA%/OctopusS1/tools/
خارج المستودع. إن وجدت نسخة gh مناسبة مسبقًا فاستعملها بدل تنزيل مكرر.
تحقق من gh --version ثم مرر المسار الكامل إلى -Gh؛ لا حاجة لتعديل PATH.

**تسجيل الدخول فعل للمالك داخل حاسبه**، مثل:
```powershell
& $ghExe auth login --hostname github.com --web
```
هنا $ghExe هو المسار الذي اكتشفه الوكيل، وليس متغيرًا معرفًا سلفًا في حاسبك.
لا تعرض أو تجمع gh auth token، ولا تطلب كلمة مرور/PAT في الدردشة.
عند اكتمال الدخول، يستخدم الوكيل الجلسة المخولة للمستودع المحدد.

## تسليم المسودة دون إعادة البناء
قبل الرفع، افحص APK الموجود والحجم والبصمة ومعرف التطبيق والتوقيع، وطابق
manifest وسجل الإصدار ونسخ test-evidence/XML المحتفظ بها. احتفظ بالسجلات
المرفوعة خالية من الأسرار؛ لا ترفع مجلد Logs كاملًا تلقائيًا.

بعد التحقق من gh والدخول، نفذ من جذر المشروع:
```powershell
.\scripts\new-draft-release.ps1 -Channel Dev -VersionCode 2 -Gh $ghExe
```
المقصود Draft Release فقط. تحقق بعد التنفيذ من isDraft=true، والمستودع
EVENTo0/octopus-S1، والنسخة/المصدر/أسماء النواتج وأحجامها.
عند وجود المسودة من محاولة سابقة، افحصها وأكملها دون نشر أو استبدال APK
مختلف بنفس الإصدار. لا تكرر create عشوائيًا ولا تستعمل --clobber لتغطية اختلاف.

سجّل رابط المسودة. وللتحقق من النقل، نزّل APK من المسودة إلى مجلد تحقق
جديد وأعد حساب SHA-256 وقارنه بالبصمة المحلية. لا تحتاج نسخة Dev جديدة
لأن النشر المصرح خاص بالتسليم لا بتغيير المحتوى.
المسودة لا تعني رابطًا عامًا؛ يراها أصحاب صلاحيات المستودع المناسبة.
لا تحوّلها إلى public prerelease لإصلاح مشكلة رؤية أو وصول.

## الهاتف والتوقيع مرحلتان مستقلتان
بعد تسليم Dev، أكمل الأعمال المستقلة التالية دون توقف شامل إذا انتظر أحدها:

1. افحص adb devices. إذا لا يوجد جهاز، جهّز قائمة التجربة وأعط المالك
   خطوة USB debugging وقبول طلب الهاتف مرة واحدة. لا تعرض serial الجهاز
   أو معرّفات خاصة في تقرير عام.
2. على جهاز مصرح به اختبر Dev 0.1.1 نفسه: تثبيت/تحديث من Dev القديمة إن
   كانت مثبتة، حركة وكاميرا بإصبعين، جمع ثلاث خلايا مرة واحدة، رفض التفعيل
   المبكر، Pause والإدخالات المحيطة به، البرج والإخلاء، إعادة المهمة،
   خلفية التطبيق، الحفظ، والعربية/الإنجليزية والنص الملتف.
3. سجّل الطراز وAndroid ودقة/إعدادات العرض ومدة الجلسة والأداء المقاس
   وlogcat المنقح. الهدف الأولي 30 FPS مستدامة؛ لا تدّع قياس FPS أو
   نجاح الجهاز من لقطة شاشة أو من الاختبارات المحقونة.
4. تحقق هل أنشأ المالك مفتاح Live بالفعل. إن لم ينشئه، جهّز أمر
   scripts/new-live-keystore.ps1 في الطرفية المحلية وأعطه للمالك لإدخال
   كلمة المرور بنفسه وحفظ نسخة احتياطية خارج Git. لا تطلب السر هنا ولا
   تنشئ هوية توقيع ثانية فوق مفتاح موجود.
5. عند توفر المفتاح ابْنِ LiveCandidate بالإصدار 0.1.1 ورقم أعلى من
   كل رقم مسجل لمعرف com.evento.octopuss1؛ الرقم 2 فقط إن بقي الأحدث 1.
   اختبر APK المرشح نفسه والتثبيت بجانب Dev والحفظ المنفصل.
6. النسخة prototype القديمة استخدمت معرف Live بتوقيع debug؛ لا تحذفها
   أو بياناتها تلقائيًا لتجاوز تعارض التوقيع. اعرض للمستخدم التعارض الفعلي
   وخيارات الاحتفاظ بالبيانات إذا ظهر.
7. لا تعتمد Live قبل اختبار المرشح وقرار المالك المرتبط بالنسخة والبصمة.
   إذا تغيرت شيفرة Unity، تعاد اختبارات المحتوى الجديد ويصدر APK برقم جديد.
   تغييرات الوثائق وحدها لا تعيد البناء أو تغير APK القائم.

## تسليم الدورة الثالثة
الترتيب: gh المحلي والدخول → Draft Release والتحقق من تنزيله → اختبار الهاتف،
مع تجهيز توقيع Live بالتوازي من حيث الأعمال المستقلة فقط.
يبقى تشغيل Unity واحدًا في checkout واحد؛ لا توزع عمليات تغيّر الإعدادات
بالتزامن. لا تبدأ CI/Cloud مدفوعًا لهذه الدورة.

يسجل الوكيل في ملف المتابعة: رابط المسودة وحالة draft وبصمة الملف المعاد
تنزيله، نتيجة الهاتف أو غيابه، LiveCandidate أو عائق المفتاح، الإجراءات التي
نفذت فعليًا، وأي عيب جديد. لا يستبدل «لا هاتف» بقبول G3، ولا «لا مفتاح»
بتسمية debug APK نسخة Live. الإنفاق المحلي لهذه الدورة والتكاليف السابقة
المجهولة يذكران بصورة منفصلة.

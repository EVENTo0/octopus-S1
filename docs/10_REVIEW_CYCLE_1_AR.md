# مراجعة الدورة الأولى وتعليمات الدورة الثانية — Octopus S1

**تاريخ المراجعة:** 26 أكتوبر 2026، بعد تقرير Claude المحلي للدورة الأولى.  
**التقرير المراجع:** OS1-LOCAL-001 / Revision 1 في
[ملف المتابعة](../OCTOPUS_S1_WORKLOG.md)، عند
`95844ca12ab54f2ab3ae38667adf1905adc03978`.  
**نطاق المراجعة:** قراءة التقرير وفروق الشيفرة وأدوات البناء والاختبارات. لم يتصل
ChatGPT بالحاسب أو الهاتف، ولم ينزل APK أو XML المحليين، ولم يُعد تشغيل Unity.

## القرار
يوجد تقدم هندسي واضح: تقرير استيراد وبناء محليين فعليين، وAPK Dev محدد،
وسبع حالات اختبار موجودة في المصدر. يُقبل ذلك كأساس للدورة التالية،
مع بقاء إثبات اللعب على الهاتف وLive المعتمدة غير منجزين.
لا يُعاد المشروع إلى scaffold، ولا تُطلب إعادة تنزيل المرجع أو ميزانية جديدة.

التقرير يذكر اختيار المالك Unity 6000.6.4f1 المثبت والمرخص على حاسبه.
يتطابق ذلك مع ProjectVersion وحارس البناء الحاليين. تُحدّث التعليمات النشطة
لتطابق هذا الإصدار؛ أدلة 6000.3.25f1 القديمة تبقى تاريخًا ولا تُفسر كأمر downgrade.

## R1 — ربط الاختبارات بمصدر البناء — أولوية P1
في [unity-local.ps1](../scripts/unity-local.ps1)،
Get-PlayModeResult يقرأ Logs/playmode.xml فقط. Invoke-AndroidBuild يفحص
result=Passed، لكنه لا يقارن المصدر الذي اختُبر بمصدر البناء ولا إصدار المحرر،
ولا يعيد التحقق من total/failed كما يفعل أمر test.

**الأثر:** تغيير مصدر ملتزم به ثم استدعاء build يمكن أن ينسب نتيجة XML قديمة
إلى APK جديد. هذه فجوة في بوابة البناء، وليست ادعاءً بأن تقرير 7/7 السابق مزور.

**المطلوب:** سجل اختبار صغير يرتبط ببصمة محتوى مصادر Unity والاختبارات
والحزم والإعدادات الفعلية وإصدار المحرر وبصمة XML. ارفض mismatch أو نتائج
مفقودة/فارغة/فاشلة. تغييرات وثيقة فقط لا تستلزم إعادة اختبارات اللعب إذا لم
يتغير المحتوى ذي الصلة؛ عرّف مجال البصمة بوضوح ولا تعتمد على وقت الملف وحده.
أعد التأكد من نفس المدخلات قبل وبعد البناء، أو ابنِ من checkout معزول ثابت.

**التحقق:** اختبارات حقيقية لرفض نتيجة من مصدر مختلف، XML Passed بصفر اختبارات،
محرر مختلف، فشل/غياب XML، والتغيير أثناء البناء. بعد الإصلاح شغّل الاختبارات
على المصدر النهائي وسجّل الدليل. لا تعِد نسبة المصدر إلى XML قديم بأثر رجعي.

## R2 — توقف محاكاة اللعب فور Pause — أولوية P1
في [OctopusS1Prototype.cs](../Assets/Scripts/OctopusS1Prototype.cs)،
Update يفحص Playing قبل ReadPointers فقط. يمكن لـ HandlePointer أن ينتقل
إلى Paused، ثم يستمر Update إلى الحركة والجمع والتفاعل. ReadPointers يواصل
أيضًا معالجة اللمسات التالية في الإطار نفسه بعد تغيير الحالة.

**الأثر:** يستطيع إطار زر Pause تنفيذ جمع قريب، وقد تعيد لمسة لاحقة تفعيل
interactRequested أثناء الإيقاف. هذا استنتاج من مسار الكود؛ لم يُعاد إنتاجه
على هاتف في هذه المراجعة.

**المطلوب:** توقف معالجة اللعب والمدخلات المخصصة له عند مغادرة Playing،
وامنع التفاعل/الجمع/الكشف/الحركة بعد الإيقاف في الإطار نفسه.
راجع ترتيب تطبيق مدخل الحركة الحالي؛ ReadKeyboard ينسخ touchMoveInput قبل
تحديثه في ReadPointers، ولذلك يقرأ قيمة الإطار السابق.

**التحقق:** إعادة إنتاج ثم اختبار يمنع جمع خلية أو تشغيل البرج/الإخلاء عند Pause،
ولمستين في الإطار نفسه، وEnded/Canceled والاستئناف دون حركة أو تفاعل عالق.
اختبر مسار المحاكاة الحقيقي، لا علم interactRequested وحده.

## R3 — استعادة إعدادات البناء والتوقيع — أولوية P1 قبل LiveCandidate
في [OctopusS1Build.cs](../Assets/Editor/OctopusS1Build.cs)،
RestoreBaseSettings لا يعيد keystoreName ولا flags التطوير/التصحيح/profiler
إلى الحالة السابقة، ويعيد قيم الإصدار إلى ثوابت بدل أخذ snapshot.
التعليق يقول إنه يمسح مسار المضيف، لكن keystoreName لا يُمسح هناك.
سكربت Windows يخفي ذلك جزئيًا عبر git restore لملف إعدادات كامل في finally؛
هذا لا يغطي المدخلات الأخرى ويمكنه إلغاء تعديل متزامن لمستخدم.

**المطلوب:** استعادة محددة للحالة السابقة أو checkout بناء معزول، تغطي النجاح
والفشل وأوامر البناء المحلية المستخدمة. لا تمسح تعديلات مالك متزامنة أو تحفظ
مسار مفتاحه الخاص في Git. احتفظ ببيانات اعتماد البيئة في الذاكرة للعملية اللازمة
فقط؛ لا تطبع قيمها. لا تغيّر إعدادات قناة أخرى أو سجل APK سابق لإرضاء فحص النظافة.

**التحقق:** مقارنة الحالة قبل/بعد نجاح وفشل مقصودين، تشمل keystoreName/alias
والمعرف والإصدار والأعلام، وفحص git diff. لا يلزم نشر أسرار أو استئجار حاسب.

## R4 — توحيد الأدلة والإعدادات النشطة — أولوية P2
- AGENTS وEmpire Prompt وREADME كانت ما تزال تشير إلى الإصدار القديم وعدم
  وجود APK. صُححت الأوامر النشطة في تحديث هذه المراجعة مع إبقاء التقارير التاريخية.
- manifest يطلب test-framework 1.4.6 بينما lock يسجل builtin 1.8.0.
  لا نجزم بأن ذلك خطأ استيراد؛ التقرير يقول إن الاستيراد نجح. وثّق قاعدة حل
  الحزمة مع المحرر الحالي، وطابق الإعلان مع النسخة المختبرة إن كان ذلك هو
  الإعداد المدعوم. لا تُعد حزمة inputlegacy المحذوفة.
- versionCode يُفحص مقابل مجلدات هذا الحاسب فقط. قبل أول Live ثم الإصدارات
  اللاحقة، استخدم سجل الإصدارات المحتفظ به أيضًا، حتى لا يُعاد رقم منشور
  على حاسب آخر أو بعد نقل مجلد النواتج.
- سجّل بصمات التوقيع كاملة في manifest المحلي/مسودة الإصدار، واحتفظ بأدلة
  الاختبارات المنقحة. لا تلخص نجاح اختبارات مصدر مختلف بوصفه قبولًا للمصدر الحالي.

## أمر الدورة الثانية OS1-LOCAL-002
1. احفظ checkpoint للعمل الجاري وزامن الأمر؛ لا تشغّل Unity مرتين على checkout واحد.
2. عالج R1 وR2، ثم R3 قبل LiveCandidate؛ اختبر حالات الفشل والتراجع المعنية.
3. طابق إعداد الحزمة/الإصدار الفعليين وسجل سبب اختيار المحرر الحالي؛ لا تبدأ Cloud جديدًا.
4. ابنِ Dev 0.1.1 بكود إصدار أعلى من كل رقم موزع/محفوظ. الافتراضي 2 فقط
   إذا لم يوجد رقم أحدث؛ احتفظ بـDev 0.1.0 (1) كأثر سابق ولا تستبدله.
5. افحص APK وتوقيعه ونسخته وبصمته وأرفق تقرير الاختبارات المرتبط بالمصدر.
   سلّمه محليًا وفي GitHub Draft Release للمالك. غياب تثبيت gh لا يتطلب
   إعادة طلب UAC باستمرار: افحص وجود أداة/جلسة مخولة، أو نسخة gh المحمولة
   الرسمية/واجهة GitHub بإذن المالك القائم؛ لا تطلب رموزًا في الدردشة.
6. على جهاز Android ARM64 مصرح به: تحقق من بصمة الملف قبل التثبيت، جرّب
   تحديث Dev إن كانت النسخة السابقة مثبتة، ثم المهمة الكاملة باللمس والعربية
   والإنجليزية وPause وخلفية التطبيق والحفظ ودورة ثانية. سجل الجهاز ومدة
   الاختبار والأداء الفعلي وlogcat المنقح. لا تحذف نسخة prototype قديمة ذات
   com.evento.octopuss1 لتجاوز تعارض توقيع Live.
7. حضّر/ابنِ LiveCandidate عند توفر مفتاح المالك ونسخته الاحتياطية خارج Git،
   ثم اختبر coexistence والحفظ المنفصل ونفس APK المرشح. دون مفتاح/هاتف،
   أنجز الإصلاحات وDev والتسليم وسجّل العائق الواحد الدقيق؛ لا تتوقف عن كل العمل.
8. حدّث ملف المتابعة وRelease register ونتائج الدورة. لا ترفع APK عامًا،
   ولا تعتمد Live أو تدمج PR تلقائيًا.

يفضل فحص الكاميرا قرب الصخور، قراءة النص العربي الملتف على الشاشة، وعدم
تزايد الموارد الأصلية مع إعادة المهمة المتكررة أثناء جلسة الجهاز. إذا ظهر
عيب فأعد إنتاجه وعالجه؛ لا تستبدل القياس بادعاء اجتياز.

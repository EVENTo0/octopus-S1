# نسختا Dev وLive — Octopus S1

> **حالة 2026-10-26:** نُفذ مدخل القناتين (Dev/LiveCandidate) وفحص APK بـ aapt2/apksigner في
> `scripts/unity-local.ps1`؛ بُني Dev 0.1.0 (1) فقط. LiveCandidate ينتظر مفتاح Live الخاص بالمالك
> (`scripts/new-live-keystore.ps1`)، والتثبيت المتزامن لم يُختبر على جهاز. الفقرة التالية تصف الحالة قبل التنفيذ.

هذه مواصفات مطلوب تنفيذها بواسطة الوكيل المحلي. البناء الحالي ينتج APK
تطويريًا واحدًا؛ لا يدعم بعد فصل القناتين أو ترقية إصدار معتمد.

## النسختان على الهاتف
يعمل مصدر Unity واحد مع إعدادين للبناء، ويمكن تثبيت النسختين معًا:

| البند | Dev — التجريبية | Live — المعتمدة |
|---|---|---|
| اسم التطبيق | Octopus S1 Dev | Octopus S1 |
| Android application ID | com.evento.octopuss1.dev | com.evento.octopuss1 |
| البيانات والحفظ | مساحة مستقلة للتجربة | مساحة مستقلة للإصدارات المعتمدة |
| إعدادات التطوير | مسموحة للتشخيص | Development/Script Debugging/Profiler معطلة |
| التوقيع | سياسة توقيع اختبار موثقة | مفتاح Live مستمر يملكه المالك |
| مكان الناتج المقترح | Builds/Android/Dev/{versionCode}/ | Builds/Android/LiveCandidate/{versionCode}/ |
| الاعتماد | قابلة للتغيير وإعادة الاختبار | نسخة APK مرشحة تختبر ثم يعتمدها المالك |

لا يُنسخ المشروع إلى مجلدين متباعدين ولا تُسمّى نسخة debug باسم Live.
اختلاف application ID يجعل بيانات Android منفصلة؛ اختبر ذلك فعليًا ولا
تفترض أن مسار حفظ مخصصًا في الشيفرة لن يعيد خلط البيانات.
أي نقل تقدم بين القناتين ميزة اختيارية لاحقة، وليس نسخًا تلقائيًا للحفظ.

لا توجد Live قبل قبول أول مرشح. بعد قبوله، يبقى APK المعتمد ووسمه محفوظين
ويستمر تطوير Dev للإصدار التالي.

## عقد البناء المطلوب
1. مدخل واحد صريح لاختيار Dev أو LiveCandidate، تستعمله السكربتات المحلية
   وCloud. إضافة الخيار مهمة تنفيذ؛ لا تفترض أن -Channel يعمل في السكربت الحالي.
2. طبّق الاسم والمعرف والقناة بعد مولّد المشهد كي لا يعيد ضبطها إلى قيم النموذج.
3. ارفض القناة غير المعروفة وتعارض الإصدار أو غياب توقيع Live.
4. اجعل versionCode متزايدًا لكل application ID، مع نسخة بشرية واضحة.
   لا تغيّر كود إصدار APK سبق توزيعه ثم تعيد استخدامه لإصدار آخر.
5. احتفظ بملف manifest بجانب APK: channel، version/versionCode، source SHA
   الكامل، Unity version، application ID الفعلي، SHA-256، بصمة شهادة التوقيع
   العامة، أعلام التطوير الفعلية، ونوع الاختبارات والأجهزة المعروفة.
6. افحص APK الناتج بأدوات Android مثل aapt/apkanalyzer وapksigner؛ ملف
   PlayerSettings وحده لا يثبت هوية التطبيق أو أن Live غير debuggable.
7. تحقق من وجود Android ARM64 ونجاح الاختبارات. مرّر أخطاء Unity للسكربت
   وارفض نتائج XML القديمة أو الفارغة والنواتج القديمة بعد فشل البناء.
8. لا تودع APK أو مفاتيح أو Unity/Library في Git. سجلات الاختبار المنقحة
   وبيانات الإصدارات الصغيرة يجوز تتبعها، دون بيانات خاصة من الجهاز.

## التوقيع والتحديثات
ثبات application ID ومفتاح توقيع القناة مطلوب لتحديث التطبيق على Android.
لا تعتمد على مفتاح debug خاص بكل حاسب كتوقيع Live مستمر.
ينشئ/يحفظ المالك هوية التوقيع بطريقة مدعومة، مع نسخة احتياطية آمنة خارج
المستودع. تُسجل البصمة العامة فقط؛ لا تنسخ السر إلى الدردشة أو worklog.

تنبيه انتقال محدد: النموذج الحالي يستخدم com.evento.octopuss1 مع توقيع debug.
إذا كان مثبتًا على الهاتف، فلا تدّع أن توقيع Live جديد سيحدّثه. سجّل تعارض
التوقيع واعرض خطة تحفظ البيانات أو اطلب قرار المالك بشأن تلك النسخة القديمة؛
لا تحذفها تلقائيًا. النسخ المعتمدة المستقبلية تحافظ على هوية توقيع Live.

اختبر تحديث Dev فوق Dev وLiveCandidate فوق Live في جهاز اختبار مصرح به
دون حذف التطبيق/الحفظ لتجاوز عدم توافق التوقيع. فشل التحديث عيب يجب تسجيله.
إذا لا توجد Live سابقة، سجّل أن اختبار ترقية Live مؤجل حتى وجود الإصدار الأول.
لا تفترض أن تثبيت APK قديم ذي versionCode أقل سيعمل دون فقد بيانات.

## سير الاعتماد
1. أصلح واختبر Dev حتى تعمل المهمة كاملة باللمس.
2. ابنِ LiveCandidate بالإعداد والتوقيع النهائيين من source SHA محدد.
3. اختبر ذلك APK نفسه: تثبيت، مهمة كاملة، حفظ، استئناف، قنوات منفصلة، أداء.
4. اعرض للمالك النسخة والبصمة والنتائج والعيوب المعروفة.
5. بعد موافقة المالك، رقِّ الملف المختبر نفسه، دون rebuild أو تغيير bytes،
   واحفظ release record ووسمًا غير قابل لإعادة التوجيه مثل v0.1.0 عند ملاءمته.
6. استمر في Dev، واحتفظ بكل Live سابقة دون استبدال APK أو الوسم.
   لا يتطلب ذلك دمج PR تلقائيًا أو إنشاء نسخ متعارضة من المشروع.

## تسليم APK للاختبار
النشر المطلوب هنا تسليم ملف قابل للتثبيت للاختبار، وليس Google Play.
اختار المالك صراحةً: APK على حاسبه وGitHub Draft Release للمالك أولًا.
سُجل القرار في OCTOPUS_S1_WORKLOG.md. تنفذ المسودة عند توفر صلاحية
الإصدارات؛ غيابها لا يمنع تسليم APK محليًا مع توثيق العائق.
المسودة متاحة لأصحاب الصلاحيات المناسبة وليست تنزيلًا عامًا لكل المختبرين.
إذا غيّر المالك اختياره لاحقًا إلى GitHub Pre-release على المستودع العام، وضّح أن APK
وبيانات الإصدار المرفوعة ستكون عامة، وانشر النواتج المصرح بها فقط.
لا تفعّل زر التحميل العام في الموقع قبل بوابة القبول المنصوص عليها في الكتالوج.

صفحة التسليم/الإصدار تتضمن: APK، SHA-256، source SHA، الإصدار والقناة،
الأجهزة المختبرة، الحد الأدنى Android، إرشادات التثبيت، العيوب المعروفة،
والتصريح بأن sideload/testing لا يمثل مراجعة متجر.
لا تسمح بنص «تم اختبار الجهاز» أو «Live معتمدة» دون دليل أو قرار المالك.
